# Handoff: assisted apply (the browser extension), 2026-09-08

For whoever picks this up. Everything below is verifiable from the repo,
the production database and the automatic page captures; nothing here is
a recollection. The rules of the system live in `docs/agents/` (start with
`observability.md`, section "Assisted apply"); this file is the state of
the work and the open defects, with evidence.

## What it is

A Chrome extension (`extension/`, load unpacked) that fills job
application forms from the person's profile, remembered answers and
drafts, asks the model once for what is still blank, and stops before
Submit. The API side is `src/api/apply.py` (the fill ladder, the profile,
the option matcher) and `src/api/routers/apply.py` (resolve, suggest,
submitted, reports). Three hand-written readers (Ashby, Greenhouse, Lever
under `extension/readers/`) and one config-driven engine
(`extension/engine.js`) that interprets a per-ATS selector table
(`extension/ats/<ATS>.js`, 50 ATSs, generated by
`tools/convert_ats_config.py` from a selector table in a common
ATS-config format; the table snapshot is outside the repo at
`~/personal/job-scripts-experiments/simplify-3.1.4/remoteConfig.json` on
Kanishk's machine and must not be named in the repo).

## Open defects, with evidence

Read captures with (production, read only):

    SELECT id, created_at, page->>'build', note FROM application_reports ORDER BY id DESC;
    SELECT f->>'key', f->>'trace' FROM application_reports, jsonb_array_elements(page->'fields') f WHERE id = <id>;

### 1. Workday field of study: the search never filters (capture 25)

The field-of-study picker is a Workday `selectinput` inside a
`multiSelectContainer`: click the box, type, Enter filters an
alphabetical list of ~100 to the matches, click the leaf (a radio). The
recipe in `extension/ats/Workday.js` (field `education`, nested group
`major`, inner field `name`, variant 0) does: click the field frame
(action 0, path names `education-%NUMBER0%`), pause, type
(`defaultWithoutBlur`, action 2), keydown+keyup Enter (actions 3 and 4),
wait 1.5 s, check a selected item (action 6), click the matching
`promptLeafNode` (action 7), all pick steps `allowFailure`.

Evidence, capture 25 trace: `typing "Computer Science" into
education-181--fieldOfStudy one key at a time` then `action 6: 45 options
shown, none close to "Computer Science": Abnormal psychology / Abrahamic
religions / Accounting ...`. The list shown after Enter is the unfiltered
alphabet, every run, across four builds.

What was measured on the same page by hand (MCP tab, page 1's
country-code box, the same widget type): setting the value whole with
one `input` event and Enter leaves the list unfiltered; typing character
by character with keydown, keypress, input, keyup, 30 ms apart, a 700 ms
pause, then keydown+keyup Enter, filtered the list to "Canada (+1)" and
selected it. The engine now types that way (`typeSlowly` in engine.js,
60 ms a key, 900 ms pause, Escape on any open popup first, a click on the
box) and the list still does not filter in the real run.

Cause found by reading the code after the last capture, fixed in this
commit, not yet verified on a live run: `runActions` dispatched a
recipe's `event` as `new Event(a.event, eventOptions)`, so the recipe's
Enter arrived as a bare `Event("keydown")` with no key, and Workday
ignored it; the hand probe that worked used a `KeyboardEvent` with key,
code, keyCode and which. `eventOf()` in engine.js now builds the event
class the name implies. If the next capture still shows the alphabet,
the hypotheses left are:

1. (was the above; done)
2. The keystrokes go to the box but the popup was opened by action 0's
   click on the frame, not by the box; the probe clicked the input itself.
   `typeSlowly` clicks the input now, so this is probably not it.
3. Workday debounces the search on real key events with `isTrusted`; if so
   no synthetic sequence will filter and the fallback is to scroll the
   virtualized list (the recipe's action 8, `scrollListboxToOption`) and
   pick by label from the whole list.

How to test quickly: on
`https://fis.wd5.myworkdayjobs.com/en-CA/searchjobs/job/US-FL-JAX-347/Forward-Deployed-Engineer_JR0307951-1/apply/applyManually`
(page 1, no login) the box `#phoneNumber--countryPhoneCode` is the same
widget. Run the engine's exact sequence there in the console and watch
`[data-automation-id="promptOption"]` labels.

### 2. Workday second education entry writes into the first block (capture 25)

Kanishk has two degrees; the profile has two education rows. Trace:
`education entry 2: filling (page number 1)` followed by `typing
"Mathematics" into education-181--fieldOfStudy`, the same block as entry
1. So the Add button for a second education block either was not found
or the new block did not appear under any `containerPath` within 4 s, and
`fillGroup` fell back to the last container (`containers[i] ||
containers[containers.length - 1]` in engine.js) and overwrote entry 1.

Fixed in this commit, unverified: when the add click does not yield a
new container the group notes it and stops instead of falling back to an
existing block. Still to find out
why the add did not work: the table's `addButtonPath` list for
`education` (aria-labels "Add Another Education", "Add Education", or
`data-automation-id="add-button"` inside the education section) against
the live page. The experience group adds five blocks fine on the same
page, so compare the two sections' Add buttons.

### 3. Degree overwritten by the field-of-study fallback (capture 23, fixed in 1f677ef, unverified)

The closest-option fallback read the degree popup that was still open
and clicked "Master of Computer Science". `optionsOnScreen` now reads only
the popup open now and `typeSlowly` presses Escape first. Capture 25 shows
the degree correct, so this is probably fixed; verify on the next run.

## Things that cost a night and should not cost the next person one

- Kanishk loads the unpacked extension from the main checkout
  `~/personal/job-scripts/extension`, not from a worktree. A fix reaches
  his browser only after merge to main, `git pull` in that checkout, and a
  reload at chrome://extensions. Check `page->>'build'` on a capture before
  debugging it.
- The MCP browser tab is parked by a tab suspender within seconds. A live
  probe is one navigate plus one script under about eight seconds.
- Never press Submit on a live form from a script; a scripted submit on
  Clera was spam-flagged from his browser.
- The table describes their selectors, not their runtime. Every place the
  engine's interpretation differs from theirs is a bug that only a live
  form shows. The audit tool measures data coverage, not behaviour.
- Readers dispatch on the widget on the page (react-select, checkboxes,
  radios, native select, textarea, file, text), never on the field's kind
  or name; the kind only tells the model what shape of answer to give.
  Three Greenhouse misses in one evening came from breaking that rule.
- Production database access is read-only except writes Kanishk asks for
  (profile edits, app_config). The DSN is in the worktree's `.env`.
